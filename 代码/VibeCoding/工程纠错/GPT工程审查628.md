# 智能物流车工程问题排查与固件分析报告

## 结论总览

当前 repo 里的"最新工程（石山）/smart_logistics_car_integrated_route_2026-06-17"确实已经把激光链路从主流程里屏蔽掉了。如果你串口仍然看到"未检测到激光导致底盘锁死"，大概率不是在跑这个最新 standalone 固件，而是在跑旧工程/旧 bin，或者 `FIXED_ROUTE_STANDALONE_ENABLE` 没有按 1 编进当前烧录镜像。若确认烧录的是这个最新工程，那车不动的重点不在激光，而在电机 RS485/USART1/驱动使能链路。

---

## 1. Repo 里的两套逻辑：旧逻辑会因激光锁车，新逻辑不会

### 旧逻辑（导致激光锁车）

旧的整合示例 `smart_logistics_car_integrated_62backup/Templates/main_integrated_example.c` 中，主循环明确：

- 只要 `snap.laser_valid == false` 或激光告警等级达到停止级别，就调用 `ChassisControl_SetExternalEmergency(1U)`。
- 否则才清告停并跑运动 demo。
- `laser_valid` 来自 `raw.laser_ok`，`sensor_bridge.c` 会在 `raw->laser_ok == 0U` 时打 `SENSOR_FAULT_LASER_INVALID`，并把 `snap->laser_valid` 设为 false。
- `laser_ok` 默认是 0，只有激光测距数据 valid 且未超时才会变成 1。
- 因此旧逻辑下，即使传感器物理连接，只要 I2C 初始化、地址、ID、数据 ready 或超时判断有任何失败，软件都会认为激光不可用并锁车。

### 新逻辑（绕开激光和 IMU 依赖）

最新工程的 `config.h` 明确：`FIXED_ROUTE_STANDALONE_ENABLE` 为 1，注释为 "no Raspberry Pi, no laser, no IMU dependency"。

在 `main.c` 中，standalone 模式下：

- `MX_I2C1_Init()` 被跳过（激光所在的 I2C1 不初始化）。
- `Board_App_Init()` 被跳过（`Laser_App_Init()` 不会被调用）。
- `Board_App_Loop()`、`RemoteCmd_Loop()`、`CSV_Debug_Loop()` 都在 `FIXED_ROUTE_STANDALONE_ENABLE == 0U` 的条件块里，当前不会运行。

---

## 2. 最新主流程实际只做三件事

1. 初始化 USART1 电机总线
2. 初始化固定路线
3. 循环执行 `CompetitionRoute_Loop()` 和 `Mecanum_PeriodicTask()`

固定路线模块默认自动启动（`COMPETITION_ROUTE_AUTO_START` 默认 1，启动等待仅 200 ms）。`CompetitionRoute_Init()` 会在 auto-start 打开时调用 `CompetitionRoute_StartDefault()`。

**所以，如果你烧的是这个最新工程，它不会因为激光没检测到而不启动。**

---

## 3. 如果串口仍然说 laser fault/laser lock，优先怀疑烧录目标不对

最新 standalone 工程里，USART2 的远程命令/状态串口在 standalone 模式下根本不初始化（`RemoteCmd_Init(&huart2)` 也不会调用），循环里 `RemoteCmd_Loop()` 同样不会运行。

因此串口反馈"没有检测到激光导致锁死"更像是以下情况之一：

1. 烧进去的不是最新工程（石山）/smart_logistics_car_integrated_route_2026-06-17 的最新产物，而是旧的整合示例或旧 Debug hex/bin。
2. CubeIDE 当前 active project 不是这个工程，或者 Debug 配置指向了另一个工程。
3. `config.h` 没有被当前编译单元正确引用，导致 `FIXED_ROUTE_STANDALONE_ENABLE` 实际没有按 1 编译。
4. 你看的串口输出来自另一个 MCU/树莓派程序，而不是这份 standalone 固件。

---

## 4. 如果确认烧录的是最新工程，车不动应查电机总线

最新工程已经把很多底盘错误"静默忽略"了，所以即使电机根本没收到命令，软件也可能表现为 READY/RUN，而不是报错。

证据如下：

- `ChassisControl_Init()` 不再根据 `MotorManager_EnableAll()` 的返回值判断是否进入 FAULT，而是调用后直接置 READY。
- `ChassisControl_SetVelocity()` 也没有再检查 FAULT/ESTOP 锁，直接设置目标速度并置 RUNNING/READY。
- 周期任务里还会把外部急停标志清掉，把 ESTOP/FAULT 状态恢复 READY。
- `MotorManager_EnableAll()` 对四个电机逐个发使能，但最后无条件返回 MECANUM_OK；`MotorManager_SetWheelRpm()` 即使命令失败，也继续发其他轮，最后同样返回 OK。
- ZDT 驱动层也被改成不等待电机响应：使能和速度下发都传 `wait_response = 0`。

### 症状分流表

| 现象 | 更可能原因 |
|------|-----------|
| 串口仍报 laser invalid / laser lock | 烧错工程、旧固件、`FIXED_ROUTE_STANDALONE_ENABLE` 未生效 |
| 串口不再报激光，但车不动 | 电机 RS485 总线、USART1 引脚、RS485 方向控制、电机地址、电机供电/使能问题 |
| 软件状态显示 RUN/READY，但轮子不转 | 当前代码不等待电机响应，状态不能证明电机真的收到命令 |

## 5. 最值得立刻查的两个硬件/配置点

**第一**：最新工程把电机总线固定在 **USART1 PA9/PA10**。

- `main.c` 初始化的是 `MX_USART1_UART_Init()`，并且 `Mecanum_Init(&huart1)`。
- `usart.c` 里 USART1 的引脚就是 PA9/PA10。
- 如果你实车 RS485 接的是以前示例里的 USART3 PB10/PB11，最新工程不会驱动它。

**第二**：`mecanum_config.h` 里 `MODBUS_USE_RS485_DIR_GPIO` 当前是 **0**，表示 MCU 不控制 RS485 的 DE/RE 方向脚。

- 注释说只有"外部/板载自动收发 RS485 模块"才适合这个设置。
- 如果你的 485 模块需要 MCU 控 DE/RE，就必须改成 1，并在 CubeMX/main.h/gpio.c 里配置 `RS485_DIR`。
- 当前 `gpio.c` 基本只开了 GPIOA/GPIOB 时钟，没有配置任何 RS485_DIR 输出脚。

## 6. 建议的排查顺序

1. **确认烧录镜像**
   - 在 CubeIDE 里只打开并编译 **最新工程（石山）/smart_logistics_car_integrated_route_2026-06-17**，Clean Project 后重新 Build/Flash。
   - 确认 `Core/Inc/config.h` 里的 `FIXED_ROUTE_STANDALONE_ENABLE` 是 1。
   - 若烧录后 USART2 还在持续输出激光状态，基本断定当前板子跑的不是这份 standalone 固件。

2. **架空车轮，用逻辑分析仪或示波器看 PA9**
   - 上电 200 ms 后，固定路线应该自动启动，`Mecanum_PeriodicTask()` 每 20 ms 左右会通过 USART1 下发四轮速度。
   - 若 PA9 没有波形 → 路线状态机没跑起来或没进周期任务。
   - 若 PA9 有波形但 RS485 A/B 没波形 → 查 485 模块供电、TX/RX 接线、DE/RE 方向脚。
   - 若 A/B 有波形但电机不转 → 查电机地址是否为 0x01/0x02/0x03/0x04、ZDT 协议寄存器是否匹配、电机使能/电源/抱闸。

3. **最小电机测试**
   临时注释掉 `CompetitionRoute_Loop()`，只保留一个固定速度命令，将问题从"路线状态机"降维到"电机总线能不能转"：

   ```c
   /* main.c while(1) 里临时测试，车轮必须架空 */
   static uint8_t test_started = 0U;
   if ((test_started == 0U) && (HAL_GetTick() > 10000U)) {
       test_started = 1U;
       (void)Mecanum_SetVelocity(0.0f, 0.1f, 0.0f); // 低速前进
   }
   Mecanum_PeriodicTask();
   HAL_Delay(10U);
   ```

## 7. 要彻底防止"旧逻辑又被激光锁住"的补丁方向

如果你后续还要用非 standalone 模式、USART2 远程命令或树莓派通信，但又想彻底忽略激光，建议不要只改 main，而是加一个全局旁路宏：

```c
/* Core/Inc/config.h */
#define LASER_SAFETY_BYPASS 1U
```

然后在 `sensor_bridge.c` 里让旁路模式下的 `laser_valid = true`、`laser_warning = 0`，不置 `SENSOR_FAULT_LASER_INVALID` 和 `SENSOR_FAULT_LASER_TOO_CLOSE`。否则旧的 `SensorSnapshot_t` 仍可能显示 `laser_valid=false`、`fault_flags` 里仍带激光 fault，后续模块一旦重新接入传感器安全判断，又会把这个 fault 当成锁车原因。

当前远程命令头文件虽然已经把 `REMOTE_CMD_ENABLE_LASER_SAFETY` 设为 0，注释也写着 "laser invalid/too-close never locks chassis"，但状态输出仍会显示传感器快照里的激光字段。

## 最核心的一句话

**当前最新工程里，激光不是阻止启动的代码路径；看到激光锁死日志就先查"是不是烧错组件"，看不到激光日志但车不动就查 USART1/RS485/电机地址和 485 方向控制。**
