# 最新工程第一轮阶段性审查报告

**审查对象**：`最新工程（石山）/smart_logistics_car_integrated_route_2026-06-17`  
**仓库**：`Chemcrin/IntelligentTransformCart`  
**主控**：STM32F103C8T6  
**审查范围**：`main.c`、`config.h`、`.ioc`、麦轮底盘控制、RS485/Modbus、电机管理、固定路线、JY61P、ATK-MS53L1M、远程命令与相关配置。  
**说明**：本文件是第一轮阶段性审查整理版，不是最终总报告。最终报告需要结合原理图、ZDTX42 手册、`.map` 文件和实测波形后定稿。

---

## 0. 核心结论

当前这个最新工程，默认配置下：

```c
#define FIXED_ROUTE_STANDALONE_ENABLE 1U
```

也就是说，当前固件是**固定路线 standalone 兜底版本**，不是完整传感器闭环版本。

在该配置下，`main.c` 会跳过：

- `MX_I2C1_Init()`
- `Board_App_Init()`
- `RemoteCmd_Init()`
- `Board_App_Loop()`
- `RemoteCmd_Loop()`

实际运行路径只剩：

```text
MX_GPIO_Init()
MX_USART1_UART_Init()
Mecanum_Init(&huart1)
CompetitionRoute_Init()
while (1) {
    CompetitionRoute_Loop();
    Mecanum_PeriodicTask();
    HAL_Delay(10);
}
```

所以，**如果当前烧录的确实是这个目录的默认固件，车不动不应再归因于“激光传感器未检测导致底盘锁死”**。这版默认根本不初始化 I2C1，也不调用激光应用层。

若还能在串口看到 `laser invalid`、`laser lock`、`laser_estop` 一类输出，优先怀疑：

1. 烧错工程；
2. 烧了旧 hex；
3. CubeIDE active project 不对；
4. `config.h` 没有被当前编译单元使用；
5. 串口输出来自另一份固件或树莓派程序。

当前“车不动”的第一嫌疑应该转移到：**USART1 → RS485 → ZDTX42 电机总线链路**。

## 2. 对“车不动”的专项判断

从当前代码看，软件状态机会在上电后尝试启动路线：

1. `CompetitionRoute_Init()` 默认 auto-start；
2. 进入 `WAIT_READY`；
3. 等待 `COMPETITION_ROUTE_BOOT_WAIT_MS=200U`；
4. `route_ready_to_start()` 清急停、清故障；
5. 进入 `RUNNING`；
6. 第一段路线是前进 3300 mm，速度 0.18 m/s。

而 `ChassisControl_PeriodicTask()` 会每 20 ms 左右计算四轮转速并调用 `MotorManager_SetWheelRpm()`。

因此，**如果这份固件真的在跑，但车轮不转，优先查以下项目：**

| 优先级 | 检查项 | 判断方法 |
|---:|---|---|
| P0 | PA9 是否有 UART 波形 | 示波器/逻辑分析仪看 PA9。没有波形，说明程序没跑到电机下发路径或烧录不对。 |
| P0 | RS485 模块是否需要 DE/RE 控制 | 当前 `MODBUS_USE_RS485_DIR_GPIO=0`，代码不控制方向脚。若用 MAX485/SP3485 这类非自动方向芯片，A/B 总线不会正常发。 |
| P0 | 电机地址是否为 0x01/0x02/0x03/0x04 | 当前代码固定四轮地址，不能自发现。 |
| P1 | ZDT 寄存器地址和指令码是否匹配你的电机固件版本 | 当前用 `0x00E0` 使能、`0x00E6` 速度模式、`0x0044` 读速度。 |
| P1 | 电机是否真的收到使能 | 当前不等应答，软件显示 READY/RUN 不能证明电机在线。 |

## 3. 第一轮问题清单

### 3.1 致命 / 条件致命

#### F1 — RS485 方向控制与硬件不匹配时，底盘必然不动

当前配置：

```c
#define MODBUS_USE_RS485_DIR_GPIO 0u
```

这会导致：

```c
RS485_TX_ENABLE()
RS485_RX_ENABLE()
```

在编译后变成空操作。

若你的 RS485 模块不是自动方向控制型，而是需要 MCU 控 DE/RE，则 USART1 虽然发了数据，但 RS485 A/B 总线可能没有被正确驱动。

这个问题比“激光锁死”更像当前车不动的根因。

#### F2 — 电机通信失败被静默吞掉，软件会假装一切正常

`MotorManager_EnableAll()` 和 `MotorManager_SetWheelRpm()` 都无条件返回 `MECANUM_OK`。

即使某个电机写失败，只是把 `online=0`，最后仍然返回 OK。

更严重的是，底盘周期任务调用 `MotorManager_SetWheelRpm()` 后也完全忽略返回值。

结果是：**电机完全没响应时，软件仍可能显示 RUNNING。**

---

### 3.2 严重问题

#### C1 — 急停和故障锁被人为削弱

`ChassisControl_PeriodicTask()` 里，如果 `g_external_emergency != 0`，只是清零，不停机；如果状态是 `EMERGENCY_STOP` 或 `FAULT`，也直接恢复 READY。

这确实解释了“把激光屏蔽掉后不再锁车”的软件路径，但副作用是：**真正的急停/故障保护也被屏蔽掉了。**

#### C2 — 上电自动启动路线，有实车安全风险

默认配置为：

```c
#define COMPETITION_ROUTE_AUTO_START 1U
#define COMPETITION_ROUTE_BOOT_WAIT_MS 200U
```

standalone 模式下不会等待树莓派心跳，也不会等待传感器稳定。路线模块初始化后会自动进入 `WAIT_READY`，200 ms 后即可进入 `RUNNING`。

调试阶段建议先改成：

```c
#define COMPETITION_ROUTE_AUTO_START 0U
```

至少先用串口命令或按键启动，避免上电车轮误动。

#### C3 — `ESTOP` 命令不是急停

远程命令里收到 `ESTOP` 后，代码调用的是：

```c
Mecanum_Stop()
```

不是：

```c
Mecanum_EmergencyStop()
```

而且还把 `ChassisControl_SetExternalEmergency(0U)` 清掉。

这不是语义上的 emergency stop，只是普通停车。

#### C4 — 电机反馈读取为空，闭环控制名义存在但实际缺半边

直线控制里会尝试读取左右轮平均 RPM。

但底层 `MotorManager_UpdateFeedback()` 没实现，导致 `rpm_fb` 永远不会刷新。

严格说，这不会阻止当前 open-loop 固定路线下发速度；它的影响是：**直线闭环的左右轮速差修正完全无效。**

#### C5 — 系统时钟只有 HSI 8 MHz

`.ioc` 里 RCC 频率是 8 MHz，`main.c` 也没有启用 PLL，SYSCLK 来源为 HSI。

我不把它直接判为“必然无法运行”，因为 F103 用 8 MHz HSI 跑 115200 UART 和 100 kHz I2C 是可以工作的。

但它会带来：

- 浮点运算余量低；
- HSI 精度不如外部晶振，UART/RS485 长时间、温漂下更容易边界化；
- DWT 微秒延时分辨率较粗；
- 后续加入 VL53L1、JY61P、CSV 输出后主循环实时性余量差。

如果板子**确实没有外部晶振**，不要盲目改 HSE ×9。可以考虑 HSI/2 ×9 = 36 MHz，但要重新确认 UART 波特率误差。

---

### 3.3 一般问题 / 维护性问题

#### M1 — 固定路线是时间开环，不是里程闭环

路线里平移距离通过“距离 / 速度”换算成持续时间执行，没有编码器、里程计或 IMU 位移估计。

旋转也默认：

```c
#define COMPETITION_ROUTE_USE_IMU_ROTATION 0U
```

即时间开环旋转。

这能跑“兜底路线”，但地面摩擦、电池电压、负载变化都会累计误差。

#### M2 — Modbus 接收逻辑是假定固定长度

`Modbus_Transceive()` 用以下方式一次性等待固定字节数：

```c
HAL_UART_Receive(g_modbus_uart, rx, rx_max_len, timeout_ms)
```

异常帧、短帧、粘包、噪声都会导致超时或 CRC 错。

当前速度写不等响应，所以这段主要影响未来反馈读取；一旦实现 `MotorManager_UpdateFeedback()`，它会成为实时性风险点。

#### M3 — 栈配置不一致

`.ioc` 配置 StackSize 是：

```text
0x800
```

但链接脚本 `_Min_Stack_Size` 是：

```text
0x400
```

如果启用远程命令，`remote_send_status()` 局部变量里有 `char tx[360]` 和多个 `char[18]`，再叠加 `snprintf()`，1 KB 栈偏紧。

#### M4 — 两套传感器快照结构重复

`sensors.c` 维护 `SENSOR_Snapshot_t`，`sensor_bridge.c` 再转换成 `SensorSnapshot_t`。

转换里还会把 `laser_ok==0` 标成 `SENSOR_FAULT_LASER_INVALID`。

当前 standalone 不跑传感器，这些代码属于“编译存在、运行不用”。后续如果恢复传感器闭环，建议合并快照层，避免故障标志来源混乱。

## 4. 对“激光被屏蔽但车还是无法启动”的重新判定

当前最新工程里，激光确实被屏蔽在运行路径之外：

- `FIXED_ROUTE_STANDALONE_ENABLE=1`；
- `MX_I2C1_Init()` 不执行；
- `Board_App_Init()` 不执行；
- `Laser_App_Init()` 不执行；
- `Board_App_Loop()` 不执行；
- `RemoteCmd_Loop()` 不执行。

所以：**车依旧无法启动，基本不是激光导致。**

当前最可能的三类原因是：

1. **烧录/工程选择错误**  
   如果还能看到激光锁车串口输出，那几乎可以断定跑的不是这个 standalone 默认固件。

2. **RS485 方向控制不匹配**  
   当前代码不控 DE/RE。若你的 RS485 板不是自动收发，电机收不到任何有效 Modbus 帧。

3. **电机协议/地址/接线不匹配，但软件不报错**  
   当前所有写指令都不等应答，`MotorManager` 也无条件返回 OK，因此“状态正常”不能证明电机真的在线。

## 5. 下一轮建议审查方向

先不要继续纠结激光。下一轮直接做**底盘链路最小闭环审查**：

1. 补充 RS485 收发器型号或模块照片，确认是否自动方向；
2. 补充 ZDTX42 的寄存器手册，核对 `0x00E0 / 0x00E6 / 0x0044` 是否对；
3. 补充一次逻辑分析仪截图：PA9、PA10、RS485 A/B，上电 1 秒内即可；
4. 补充当前烧录的 hex/bin 来源，是 CubeIDE 现场 build 出来的，还是 repo 里的 Debug 产物。

下一轮可以直接做一版“**只验证四个电机能不能转**”的最小测试代码，把固定路线、传感器、远程命令全部旁路掉。
