## 1. 审查结论摘要

本项目代码结构清晰、模块划分合理、文档记录详尽。核心的运动学逆解、Modbus RTU 帧封装、传感器驱动、远程命令协议和固定路线执行器在语法层面都是**完整且可编译**的。

但存在 **2 个致命级问题** 和 **4 个严重级问题**，按当前固件直接烧录上电**不能安全进入正常工作状态**。主要风险来自：

| 风险 | 等级 | 影响 |
|------|------|------|
| 系统时钟仅 8 MHz（未启用 PLL） | 🔴 致命 | CPU 性能仅理论值 1/9，所有外设时序受影响 |
| 电机反馈读取函数为空桩 | 🔴 致命 | 直线闭环的轮速差修正永不生效 |
| Standalone 模式 200ms 后自动行驶 | 🟠 严重 | 上电即冲下台面，人身财产风险 |
| RS485 方向控制依赖硬件（宏设为 0） | 🟠 严重 | 若硬件不支持自动方向切换，总线冲突 |
| 栈空间 1024 字节远不足 | 🟠 严重 | 深嵌套时栈溢出导致 HardFault |
| 上电即发 Modbus 使能所有电机 | 🟠 严重 | 总线未稳定即操作，可能导致误动 |

## 3. 问题清单（按严重度分级）

### 3.1 🔴 致命 (FATAL)

#### F1 — 系统时钟仅 8 MHz HSI，未启用 PLL

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Src/main.c:146-176`、`.ioc:RCC.PLLCLKFreq_Value=8000000` |
| **当前代码** | `RCC_OscInitStruct.PLL.PLLState = RCC_PLL_NONE;`、`RCC_ClkInitStruct.SYSCLKSource = RCC_SYSCLKSOURCE_HSI;` |
| **实际频率** | SYSCLK = HSI = **8 MHz**，HCLK = 8 MHz，APB1 = APB2 = 8 MHz |
| **理论最高** | STM32F103C8T6 最大 **72 MHz**（HSE 8 MHz × PLL x9） |

**影响分析**:

- CPU 性能仅为理论值的 **1/9**，浮点运动学计算耗时增大
- `Modbus_DelayUs()` 使用 DWT 周期计数器，8 MHz 下仅 **8 cycles/μs**，`MODBUS_TX_SETTLE_US=20` 仅 160 周期，精度无法保证
- I2C 100 kHz 在慢时钟下 SCL 时序裕量不足
- UART 115200 bps 的字符间时序偏差增大
- 所有 `HAL_Delay(10)` 实际耗时更长（但相对 CPU 慢，不影响绝对时间）

**建议修复**:

```c
// === 在 SystemClock_Config 中启用 HSE + PLL ===
RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_HSE;
RCC_OscInitStruct.HSEState = RCC_HSE_ON;
RCC_OscInitStruct.HSEPredivValue = RCC_HSE_PREDIV_DIV1;
RCC_OscInitStruct.PLL.PLLState = RCC_PLL_ON;
RCC_OscInitStruct.PLL.PLLSource = RCC_PLLSOURCE_HSE;
RCC_OscInitStruct.PLL.PLLMUL = RCC_PLL_MUL9;  // 8 MHz * 9 = 72 MHz

RCC_ClkInitStruct.SYSCLKSource = RCC_SYSCLKSOURCE_PLLCLK;
RCC_ClkInitStruct.AHBCLKDivider = RCC_SYSCLK_DIV1;
RCC_ClkInitStruct.APB1CLKDivider = RCC_HCLK_DIV2;   // APB1 ≤ 36 MHz
RCC_ClkInitStruct.APB2CLKDivider = RCC_HCLK_DIV1;
// Flash: 72 MHz 需要 2 等待周期
HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2);
```

#### F2 — 电机反馈功能完全为空

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Src/motor_manager.c:86-89` |
| **当前代码** | `MecanumResult_t MotorManager_UpdateFeedback(void) { return MECANUM_OK; }` |
| **调用关系** | `ChassisControl_PeriodicTask()` 每 50ms 调用一次 → 什么也不做 |

**影响链**:

1. `g_motor_states[N].rpm_fb` 始终为 **0.0f**
2. `straight_read_left_right_rpm()` → 始终返回 0 RPM
3. `g_straight_status.using_motor_feedback = 0U`
4. 左右轮差 PID（`g_lr_pid`）**永远不被更新**
5. 直线闭环仅靠航向 PID 工作，缺少轮速反馈修正

**建议修复**:

```c
MecanumResult_t MotorManager_UpdateFeedback(void)
{
    uint8_t i;
    MecanumResult_t ret;

    for (i = 0u; i < MOTOR_COUNT; i++) {
        ret = ZDTX42_ReadMotorSpeed(g_motor_addr[i], &g_motor_states[i].rpm_fb);
        if (ret == MECANUM_OK) {
            g_motor_states[i].online = 1u;
            g_motor_states[i].timeout_cnt = 0u;
        } else {
            g_motor_states[i].online = 0u;
            g_motor_states[i].timeout_cnt++;
        }
    }
    return MECANUM_OK;
}
```

**注意**: 4 个电机顺序读取，每个约 10ms 超时。改为轮询方式（每周期只读 1 个电机）避免阻塞。

### 3.2 🟠 严重 (CRITICAL)

#### C1 — Standalone 模式下上电 200ms 后自动行驶

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Inc/config.h:5`、`UserModules/competition_route/competition_route.c:364-366` |
| **当前配置** | `FIXED_ROUTE_STANDALONE_ENABLE = 1U` + `COMPETITION_ROUTE_AUTO_START = 1U` |

**执行路径**:

```
main() → CompetitionRoute_Init() → CompetitionRoute_StartDefault()
  → state = COMP_ROUTE_STATE_WAIT_READY
  → CompetitionRoute_Loop() → route_ready_to_start()
  → (FIXED_ROUTE_STANDALONE_ENABLE 非0, 跳过 RPi 心跳检查)
  → 200ms 后 state = COMP_ROUTE_STATE_RUNNING
  → 开始执行 12 步路线（先前进 3.3m）
```

**风险**: 若小车在工作台/运输包装中上电，将立即冲下台面。**这是最紧急的安全问题**。

**建议**:

| 场景 | 建议配置 |
|------|---------|
| 调试/开发 | `COMPETITION_ROUTE_AUTO_START = 0U`（保持 `IDLE`，通过 RPi 命令启动） |
| 正式比赛 | `FIXED_ROUTE_STANDALONE_ENABLE = 1U` + `COMPETITION_ROUTE_AUTO_START = 1U` |
| 带 RPi 模式 | `FIXED_ROUTE_STANDALONE_ENABLE = 0U`，依赖 RPi 心跳 |

#### C2 — RS485 方向控制宏与实际硬件可能不匹配

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Inc/mecanum_config.h:71-84`、`Core/Src/modbus_rtu.c:27-39` |
| **当前代码** | `#define MODBUS_USE_RS485_DIR_GPIO 0u` |
| **表现** | `RS485_TX_ENABLE()` / `RS485_RX_ENABLE()` 全部为空操作 |

**场景分析**:

| 实际 RS485 芯片 | 是否兼容 | 说明 |
|---|---|---|
| MAX13487 / MAX13488 (带自动方向) | ✅ 兼容 | 硬件自动切换，无需 GPIO |
| MAX485 / SP3485 (需 DE/RE) | ❌ **不兼容** | 无 GPIO 控制，总线上无人驱动或冲突 |
| 带自动方向检测的模块（如某宝常见自动切换模块） | ✅ 一般兼容 | 但需确认切换阈值和延迟是否匹配 115200bps |

**建议**:

1. 确认实际 RS485 收发器型号
2. 若需 GPIO 控制：`#define MODBUS_USE_RS485_DIR_GPIO 1u`，在 CubeMX 中将 PB1 配为 Output
3. 在 `Modbus_SendRaw` 中检查方向切换时序（当前先 `RX_ENABLE` 再 `TX_ENABLE` 的序列需确认）

#### C3 — 系统栈空间可能严重不足

| 属性 | 内容 |
|------|------|
| **文件**:行 | `STM32F103C8TX_FLASH.ld:42` |
| **当前值** | `_Min_Stack_Size = 0x400`（**1024 字节**） |
| **IOC 配置** | `ProjectManager.StackSize=0x800`（2048 字节）——但**链接脚本未同步此值** |

**最大栈路径分析**:

```
USART2_IRQHandler (中断)
  └→ HAL_UART_IRQHandler → RemoteCmd_UartRxCpltCallback (小)

正常主循环 (无中断嵌套):
  main()
    └→ RemoteCmd_Loop()                              ~50 bytes
        └→ Sensor_GetSnapshot(&snap)                  SensorSnapshot_t ~36 bytes
            └→ Board_App_GetSensorSnapshot(&raw)
                └→ sensor_get_snapshot()              SENSOR_Snapshot_t ~40 bytes
        └→ remote_handle_line()
            └→ remote_send_status()                   tx[360] + 7*char[18] ≈ 486 bytes
                └→ milli_to_text() 多次调用
                └→ snprintf() 内部缓冲区              ~100+ bytes (lib 实现相关)
              ≈ 600+ bytes
```

**估计峰值栈需求**: ~900-1100 字节，**已接近或超过 1024 字节**。

**建议**: 将 `_Min_Stack_Size` 改为 `0x800`（2048 字节），同时在 `remote_send_status()` 中缩小 `tx` 缓冲区或将大字符串拆分为多次 `HAL_UART_Transmit`。

#### C4 — 上电即使能所有电机

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Src/chassis_control.c:45` |
| **当前代码** | `ChassisControl_Init() → MotorManager_EnableAll(1u)` |

**问题**:

1. `Mecanum_Init()` 中先后调用 `Modbus_Init(&huart1)` 和 `ChassisControl_Init()`，中间无延迟
2. UART1 刚初始化完成、RS485 收发器可能尚未稳定，即发送 Modbus 帧
3. `ZDTX42_EnableMotor` 调用 `Modbus_WriteMultipleRegisters` 时 `wait_response=0`，**不等待电机响应**
4. 即使电机不存在或通信失败，`g_motor_states[i].online` 也被错误置为 `1u`

**建议**:

```c
void ChassisControl_Init(void)
{
    MotorManager_Init();
    StraightControl_Init();
    // ... 初始化变量 ...

    HAL_Delay(100);  // 等待 RS485 总线稳定

    (void)MotorManager_EnableAll(1u);
    g_chassis_state = MECANUM_STATE_READY;
}
```

同时修改 `ZDTX42_EnableMotor`，对非广播地址应等待响应：

```c
return Modbus_WriteMultipleRegisters(motor_id, ZDT_REG_ENABLE, regs, 2u, 1u);
                                                                    // ↑ 改为等待响应
```

### 3.3 🟡 一般 (MINOR)

#### M1 — Modbus_Transceive 固定长度接收

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Src/modbus_rtu.c:121` |
| **当前代码** | `HAL_UART_Receive(g_modbus_uart, rx, rx_max_len, timeout_ms)` |

`HAL_UART_Receive` 要求精确接收 `rx_max_len` 字节。若从机返回的 Modbus 帧异常（异常码仅 5 字节），函数将阻塞等待直到超时（10ms）。连续异常时，20ms 的底盘控制周期会被多个 10ms 超时严重打乱。

**建议**:
- 使用 `HAL_UART_Receive_IT` + 状态机 + 硬件超时检测
- 或至少先接收 1 字节头，再根据长度字段接收剩余字节

#### M2 — CRC 错误丢弃，无重试机制

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Src/modbus_rtu.c:128-137` |

CRC 错误时直接返回 `MECANUM_CRC_ERROR`，调用链：
`Modbus_ReadInputRegisters → ZDTX42_ReadMotorSpeed → (目前永不被调用)`

虽然当前无实际影响（因为 `MotorManager_UpdateFeedback` 为空），但未来实现反馈读取后，一次 CRC 错误就丢弃会导致偶发性数据缺失。

**建议**: 在 Modbus 层添加自动重试（至少 1 次），且在 `MotorManager` 层对连续失败计数。

#### M3 — 直线控制默认状态代码与文档不一致

| 属性 | 内容 |
|------|------|
| **文件**:行 | `Core/Inc/mecanum_config.h:50` vs `Docs/工程变更说明_2026-06-16.md` |
| **代码值** | `#define STRAIGHT_CONTROL_ENABLE_DEFAULT 0u`（默认关闭） |
| **文档值** | "上电默认启用直线控制 → `1u`" |

需决定实际行为并统一。

#### M4 — 竞争路线旋转闭环 IMU 功能未启用

| 属性 | 内容 |
|------|------|
| **文件**:行 | `UserModules/competition_route/competition_route.h:67-68` |
| **当前值** | `#define COMPETITION_ROUTE_USE_IMU_ROTATION 0U` |

旋转动作使用 **纯时间开环**——调用 `Mecanum_Rotate(wz)` 并等待计算的时间过去。没有 IMU yaw 作为反馈，在负载变化、地面摩擦不均时角度偏差会积累。

**建议**: 实现 IMU 闭环旋转（利用 `Sensor_GetSnapshot` 的 `yaw_rad`），参考已在 `competition_route.c` 中预留的 `g_route_status.rotate_target_yaw_rad` 和 `rotate_error_rad` 字段。

#### M5 — 两套传感器快照系统冗余

| 属性 | 内容 |
|------|------|
| **文件** | `Core/Inc/sensors.h`（`SENSOR_Snapshot_t`）+ `Core/Inc/sensor_bridge.h`（`SensorSnapshot_t`） |

`SENSOR_Snapshot_t`（sensors.h, 22 字段）由 `sensor_update()` 填充，`SensorSnapshot_t`（sensor_bridge.h, 12 字段）由 `Sensor_BuildSnapshot()` 从前者转换得到。两个结构体字段高度重叠，存在：

- 数据重复 + RAM 浪费（两个全局快照实例）
- 转换过程的 CPU 开销
- 维护负担（增减字段需同步修改两个结构体和转换函数）

**建议**: 统一为 `SENSOR_Snapshot_t`，移除 `sensor_bridge.c` 中的转换逻辑。

### 3.4 🔵 建议 (SUGGESTION)

| # | 建议 | 说明 |
|---|------|------|
| S1 | **使用 DMA 发送 CSV/状态帧** | `HAL_UART_Transmit` 阻塞发送 360 字节 ≈ 31ms @115200。主循环周期 10ms，单次阻塞直接打乱 3 个周期。建议 USART2 TX 用 DMA |
| S2 | **添加独立看门狗 IWDG** | 当前无看门狗。建议在 `HAL_MspInit` 中配置 IWDG 超时 4s，主循环中 `HAL_IWDG_Refresh` |
| S3 | **确认编译器优化级别** | IOC 中 `CompilerOptimize=6`（GCC `-O2`），需确认实际构建环境（STM32CubeIDE 的 -Og 调试默认 vs -O2 发布） |
| S4 | **条件编译屏蔽未使用的正运动学** | `Mecanum_ForwardKinematics` 函数已实现但全局无调用，可 `#if 0` 屏蔽 |
| S5 | **USART1（电机总线）建议开启中断** | 当前 Modbus 完全阻塞式收发，主循环 `HAL_Delay(10)` 期间无法处理 RS485 数据。开启中断后可异步接收 |
| S6 | **主循环顺序考虑** | 当前：`Board_App_Loop → CSV → RemoteCmd → CompetitionRoute → Mecanum_PeriodicTask → HAL_Delay(10)`。建议将 `Mecanum_PeriodicTask` 放在最前或使用定时器触发，确保 20ms 底盘控制周期不因前面函数的阻塞延迟而抖动 |

## 4. 上电运行可行性判定

### 结论：❌ 不能安全进入正常工作状态

以下为阻止上电即正常运行的**阻塞因素清单**，按必须修复的优先级排序：

| 优先级 | 问题 | 等级 | 影响 |
|--------|------|------|------|
| P0 | **Standalone 模式 200ms 后自动行驶 (C1)** | 🟠 严重 | 上电即冲出工作台，**必须先修复或改配置再烧录** |
| P0 | **系统时钟 8 MHz (F1)** | 🔴 致命 | 所有外设和计算性能严重不足，**必须先修复** |
| P1 | **电机反馈空桩 (F2)** | 🔴 致命 | 直线闭环的轮速差修正永远无效，影响控制精度 |
| P1 | **栈空间 1024 字节 (C3)** | 🟠 严重 | 实测 `remote_send_status` 时可能栈溢出 HardFault |
| P2 | **RS485 方向控制不确定 (C2)** | 🟠 严重 | 需确认硬件型号，否则总线可能通信失败 |
| P2 | **上电即发 Modbus 使能电机 (C4)** | 🟠 一般 | 总线未稳即操作，可能误动 |

### 上电初始化安全审查清单

| 检查项 | 结果 | 备注 |
|--------|------|------|
| 启动文件栈顶指针 `_estack` | ✅ 正确 | `0x20005000`（20KB RAM 末尾） |
| 系统时钟初始化前外设状态 | ⚠️ 安全 | GPIO 默认浮空输入 |
| USART1 TX(PA9) 初始化前电平 | ⚠️ 浮空输入 | RS485 驱动输入在高阻态，模块特性决定总线状态 |
| RS485 总线初始状态 | ❓ 不确定 | 取决于硬件模块，代码中 DE/RE 无控制 |
| 电机上电初始状态 | ⚠️ 潜在风险 | `ChassisControl_Init()` 立即使能全部电机 |
| I2C1 初始化（Standalone 模式） | ⚠️ 跳过 | `MX_I2C1_Init()` 被 `#if` 排除，激光/IMU 不工作 |
| 中断优先级分组 | ✅ 正确 | `NVIC_PRIORITYGROUP_4`（4 位抢占优先级） |
| 看门狗 | ✅ 未启用 | 无意外复位风险，但也无故障保护 |
| VL53L1 库初始化状态 | ⚠️ 在 Standalone 模式下不会执行 | 不会因找不到传感器而阻塞 |

## 6. 需要你补充的材料或确认的事项

### 6.1 必须确认（影响问题定级和修复方案）

| # | 确认项 | 影响的问题 | 说明 |
|---|--------|-----------|------|
| Q1 | **实际 RS485 收发器型号？** 是否带自动方向控制？ | C2 | 决定是否需要飞线 DE/RE 到 PB1 并启用 `MODBUS_USE_RS485_DIR_GPIO=1` |
| Q2 | **HSE 外部 8 MHz 晶振是否焊接？** 对应引脚？ | F1 | PLL 修复的前提条件。若未焊晶振，需改为 HSI+PLL（但 HSI 精度有限，会影响 USART 波特率） |
| Q3 | **VL53L1 API 编译后的 .text 段大小？** | — | 提供一次完整 Build 后的 `.map` 文件或 `arm-none-eabi-size` 输出，评估 Flash 余量是否足够容纳 VL53L1 完整 API |
| Q4 | **RS485 模块上电默认方向？** | C4 | 模块上电后 DE/RE 默认电平，是否会导致总线上电瞬间异常输出 |

### 6.2 建议提供（辅助更精确的评估和修复）

| # | 材料 | 用途 |
|---|------|------|
| D1 | **完整 Build 后的 `.map` 文件** | 精确 Flash/RAM 占用分析，VL53L1 库大小，栈/堆使用估算 |
| D2 | **RS485 模块的型号或原理图** | 确认方向控制方式、供电电压、是否隔离 |
| D3 | **完整板级原理图 PDF** | 检查电源域、上电时序、传感器接口电平、引脚冲突 |
| D4 | **ZDTX42 电机 Modbus 寄存器手册** | 验证 `ZDT_REG_SPEED_FEEDBACK`(0x0044)、`ZDT_REG_ENABLE`(0x00E0) 等地址和数值定义是否正确 |
| D5 | **当前 STM32CubeIDE Build 配置截图** | 确认编译器版本、优化级别、预定义宏 |

### 6.3 建议的修复顺序

```
Phase 1 — 安全阻塞项（上电前必须先修）
  ├── C1: 将 COMPETITION_ROUTE_AUTO_START 改为 0U
  ├── F1: 启用 HSE+PLL → 72 MHz
  └── C3: 链接脚本 StackSize 改为 0x800

Phase 2 — 核心功能修复
  ├── F2: 实现 MotorManager_UpdateFeedback()
  ├── C2: 确认 RS485 型号，配置方向控制
  └── C4: 延迟电机使能 + 等待响应

Phase 3 — 功能完善
  ├── M1: Modbus 改中断接收
  ├── M5: 合并快照结构体
  └── M4: 启用 IMU 闭环旋转

Phase 4 — 优化
  ├── S1: USART2 TX 改用 DMA
  ├── S2: 添加 IWDG
  └── 冗余代码裁剪
```
