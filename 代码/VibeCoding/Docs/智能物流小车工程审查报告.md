# 智能物流小车 STM32 工程审查报告

> 审查对象：`smart_logistics_car_integrated.zip`  
> 审查基准：`智能物流小车-硬件平台技术手册V3.md`  
> MCU / IDE：STM32F103C8T6 + HAL + STM32CubeIDE  
> 结论等级：工程框架基本成型，但存在若干会直接影响联调的 P0/P1 问题，尤其是电机串口链路、USART 中断接收、激光测距参数和 V3 全局变量命名不一致。

---

## 1. 审查依据与判定原则

本次审查将《智能物流小车硬件平台技术手册 V3》作为最高硬件标准。该手册定义的核心硬件链路为：

- 树莓派 4B 通过 USB → CH340N → STM32 `USART2` 通信，STM32 端引脚为 `PA2/PA3`。
- JY61P 与 ATK-MS53L1M/VL53L1X 共用 STM32 `I2C1`，引脚为 `PB6/PB7`。
- ZDT_X42 电机通过 RS485 接入 STM32 `USART1`，引脚为 `PA9/PA10`。

手册个别章节的数据模型表中仍出现 `USART3` 表述，但第 1.2 物理链路、第 2.1 引脚表、第 2.3 引脚占用原则和第 4.2 电机链路均指向 `USART1/PA9/PA10`。因此本报告按 `USART1/PA9/PA10` 作为电机链路的最终判定标准。

---

## 2. 工程总体内容理解

### 2.1 工程结构

工程是一个 STM32CubeIDE HAL 工程，主目录包含：

```text
smart_logistics_car_integrated/
├── Core/
│   ├── Inc/                 # 应用层、底层驱动头文件
│   └── Src/                 # main、外设初始化、传感器、电机、底盘控制代码
├── Drivers/                 # CMSIS、STM32 HAL、VL53L1X API
├── UserModules/
│   ├── remote_cmd/          # 当前纳入构建的树莓派串口命令模块
│   ├── bringup_mode/        # 预留联调/自检模块，当前未纳入构建
│   └── sensor_uart3_stream_test/ # 传感器串口流测试模块，当前未纳入构建
├── Debug/                   # 已生成过的 Debug 构建产物
└── smart_logistics_car_integrated.ioc
```

`.cproject` 当前只把 `Core`、`Drivers` 和 `UserModules/remote_cmd` 纳入构建；`bringup_mode` 与 `sensor_uart3_stream_test` 存在源码，但不是当前活动构建路径的一部分。

### 2.2 当前启动流程

`Core/Src/main.c` 的当前流程如下：

1. `HAL_Init()` 与 `SystemClock_Config()`。
2. 初始化 `GPIO`、`I2C1`、`USART1`、`USART2`、`USART3`。
3. `Board_App_Init()` 初始化传感器应用层。
4. `Mecanum_Init(&huart3)` 初始化麦轮/电机控制链路。
5. `RemoteCmd_Init(&huart2)` 初始化树莓派串口命令接收。
6. 主循环每 10 ms 调用：
   - `Board_App_Loop()`：更新 IMU 与激光数据。
   - `RemoteCmd_Loop()`：解析远程命令、执行安全逻辑、周期上报状态。
   - `Mecanum_PeriodicTask()`：执行底盘控制、电机刷新和故障检查。

### 2.3 传感器模块现状

JY61P 模块已经具备完整 I2C 驱动和应用层：

- 地址使用 `0x50` / HAL 8-bit `0xA0`。
- 从 `0x34` 起连续读取 26 字节。
- 实现加速度、角速度、欧拉角、温度转换。
- 实现静止检测、陀螺零偏校准、Yaw 归零和车体系变量映射。

ATK-MS53L1M/VL53L1X 模块已经具备完整 I2C 驱动和应用层：

- 地址使用 `0x29` / HAL 8-bit `0x52`。
- 使用 VL53L1X API 进行模块初始化、测距启动和结果读取。
- 实现中值/平均滤波、跳变抑制、有效距离判断、预警/减速/过近标志。

`sensors.c` 与 `sensor_bridge.c` 已经把 IMU、激光数据整理为快照接口，供远程命令和底盘控制使用。

### 2.4 麦轮、电机与底盘控制模块现状

麦轮模块已经拆分为较清晰的层次：

- `mecanum_kinematics.c`：速度矢量到四轮速度的运动学换算。
- `chassis_control.c`：目标速度、命令超时、电机刷新、急停和状态机。
- `motor_manager.c`：四个 ZDT_X42 电机的启停、速度设置、反馈轮询。
- `modbus_rtu.c`：Modbus RTU 帧发送、接收、CRC 校验。
- `zdt_x42_modbus.c`：ZDT_X42 相关寄存器读写封装。

从软件架构看，麦轮模块已经具备“速度指令 → 四轮 RPM → Modbus/ZDT_X42”的主链路。

### 2.5 树莓派远程命令模块现状

`UserModules/remote_cmd` 当前采用 ASCII 行协议，支持：

- `HB`：心跳。
- `STOP`：停车。
- `ESTOP`：急停。
- `CLR` / `CLEAR`：清除急停或故障锁。
- `ZERO`：IMU yaw 归零。
- `STAT?` / `STATUS?`：状态查询。
- `VEL <vx> <vy> <wz>`：速度控制。

该模块设计思路适合早期串口联调，但还不是手册建议的带帧头、序号、类型、长度和 CRC16 的正式通信协议。

## 4. 违背或疑似违背手册的问题清单

### P0-01：电机 RS485 链路实际绑定到 `USART3`，违背最高硬件标准

**工程现象**

`Core/Src/main.c` 中声明了 `huart2` 和 `huart3`，并在初始化阶段调用：

```c
Mecanum_Init(&huart3);
RemoteCmd_Init(&huart2);
```

`USART3` 在工程中配置为 `PB10/PB11`。而手册最高硬件标准要求 ZDT_X42 经 RS485 接入 `USART1`，也就是 `PA9/PA10`。

**影响**

如果硬件按手册接线，电机 RS485 模块接在 `PA9/PA10`，当前固件却从 `PB10/PB11` 发送 Modbus 帧，四个 ZDT_X42 电机不会响应。该问题会直接导致底盘电机无法联调。

**整改建议**

将 `main.c` 改为：

```c
extern UART_HandleTypeDef huart1;
extern UART_HandleTypeDef huart2;

Board_App_Init();
Mecanum_Init(&huart1);
RemoteCmd_Init(&huart2);
```

若 `USART3` 暂时保留为调试串口，应明确标注为非生产链路，不能再作为电机链路使用。

---

### P0-02：树莓派 `USART2` 接收中断未启用，`RemoteCmd` 实际收不到命令

**工程现象**

`RemoteCmd_Init()` 使用：

```c
HAL_UART_Receive_IT(g_remote_uart, &g_rx_byte, 1U);
```

但是当前 `stm32f1xx_it.c` 没有 `USART2_IRQHandler()`，`.ioc` 也没有启用 USART2 全局中断。启动文件中的 `USART2_IRQHandler` 仍会落到弱定义 `Default_Handler`。

**影响**

树莓派通过 CH340N 发送的命令不会进入 `HAL_UART_RxCpltCallback()`，`VEL`、`HB`、`STOP`、`ESTOP` 等远程命令链路不可用。由于命令心跳无法刷新，底盘也可能持续处于超时/急停逻辑中。

**整改建议**

在 CubeMX/CubeIDE 中启用 `USART2 global interrupt`，并生成或补充：

```c
extern UART_HandleTypeDef huart2;

void USART2_IRQHandler(void)
{
    HAL_UART_IRQHandler(&huart2);
}
```

若电机链路迁回 `USART1` 后需要接收电机反馈，也建议同步启用 `USART1 global interrupt` 或明确采用阻塞式 Modbus 接收策略。

---

### P1-01：ATK-MS53L1M/VL53L1X 测距参数不符合 V3 手册

**工程现象**

手册要求当前代码按 VL53L1X API 适配，并使用：

- Long 模式。
- Timing Budget `140000 us`。
- Inter-measurement `150 ms`。

工程当前实际设置为：

```c
VL53L1_SetMeasurementTimingBudgetMicroSeconds(..., 50000U);
VL53L1_SetInterMeasurementPeriodMilliSeconds(..., 50U);
```

并且 `MS53L1M_UPDATE_PERIOD_MS` 定义为 `20U`。

**影响**

测距刷新节奏与手册规定的 100–200 ms 激光状态更新建议不一致。50 ms/20 ms 的配置会增加 I2C 占用，也可能降低 Long 模式下的稳定性。

**整改建议**

统一改为：

```c
#define MS53L1M_UPDATE_PERIOD_MS 150U

VL53L1_SetMeasurementTimingBudgetMicroSeconds(&g_vl53l1_dev, 140000U);
VL53L1_SetInterMeasurementPeriodMilliSeconds(&g_vl53l1_dev, 150U);
```

若后续确实需要更高频测距，应先更新手册并记录实测依据。

---

### P1-02：IMU 与激光全局变量命名未完全同步 V3 标准

**工程现象**

手册 V3 规定 IMU 推荐变量为：

```c
g_imu_car_yaw_est_deg
g_imu_car_pitch_deg
g_imu_car_roll_deg
g_imu_gyro_yaw_dps
g_imu_acc_forward_g
g_imu_acc_right_g
g_imu_acc_down_g
g_imu_temperature_c
g_imu_valid
g_imu_calibrated
```

工程当前主要发布的是旧兼容名：

```c
car_yaw_est_deg
car_pitch_deg
car_roll_deg
gyro_yaw_dps
acc_forward_g
acc_right_g
acc_down_g
temperature_c
imu_valid
imu_calibrated
```

同时也发布了一组原始 IMU 变量，例如 `g_imu_roll_deg`、`g_imu_pitch_deg`、`g_imu_ax_g`，但这些不是 V3 推荐的车体系 `g_imu_car_* / g_imu_acc_* / g_imu_gyro_*` 命名。

激光模块也存在类似问题。手册推荐：

```c
g_laser_filtered_distance_mm
g_laser_valid
g_laser_ok
g_laser_is_warning
g_laser_is_slow
g_laser_is_too_close
g_laser_last_valid_ms
```

工程当前发布的是：

```c
g_laser_distance_mm
g_laser_raw_distance_mm
g_laser_status
g_laser_last_tick_ms
laser_ok
laser_warning
laser_slow
laser_too_close
```

**影响**

模块内部能运行，但与 V3 手册的对外接口不一致。后续树莓派联动、日志模块、状态机或其他开发者按手册变量名接入时会找不到变量或误用原始坐标系变量。

**整改建议**

新增 V3 推荐变量，并把旧变量作为兼容别名保留一段时间。例如：

```c
volatile float g_imu_car_yaw_est_deg;
volatile float g_imu_car_pitch_deg;
volatile float g_imu_car_roll_deg;
volatile float g_imu_gyro_yaw_dps;
volatile float g_imu_acc_forward_g;
volatile float g_imu_acc_right_g;
volatile float g_imu_acc_down_g;
volatile float g_imu_temperature_c;
volatile uint8_t g_imu_valid;
volatile uint8_t g_imu_calibrated;
```

激光侧同理补齐 `g_laser_filtered_distance_mm`、`g_laser_valid`、`g_laser_ok`、`g_laser_is_warning`、`g_laser_is_slow`、`g_laser_is_too_close`、`g_laser_last_valid_ms`。

### P1-03：激光无效数据被直接升级为急停，和手册“异常标记无效”原则不完全一致

**工程现象**

`remote_apply_safety()` 中只要满足以下任一条件，就进入激光急停锁：

```c
snap == NULL
snap->laser_valid == false
snap->laser_warning >= REMOTE_CMD_LASER_STOP_LEVEL
```

**影响**

这是一种偏安全策略，但它把“传感器暂时无效/未初始化”和“障碍物过近”合并为同一种激光急停结果。手册要求距离异常时应标记无效，不应直接覆盖安全状态。当前逻辑可能导致激光模块短暂超时、上电初始化未完成或 I2C 抖动时直接锁车。

**整改建议**

建议拆分为三类状态：

1. `laser_valid == false`：进入传感器故障/降级状态，限制速度或禁止自动运行，但不要伪装成障碍物过近。
2. `laser_is_too_close == true`：触发硬停车。
3. 连续多次无效或超时：置位 `FAULT_SENSOR_LASER`，等待恢复或人工清除。

### P1-04：RS485 方向控制未落地

**工程现象**

`mecanum_config.h` 中：

```c
#define MODBUS_USE_RS485_DIR_GPIO 0u
```

`modbus_rtu.c` 中的方向控制宏因此为空操作。

**影响**

如果实际 RS485 模块是自动收发方向模块，则可以运行，但需要在硬件记录中说明。若使用 MAX485 一类需要 `DE/RE` 控制的模块，当前代码只能发送或只能接收，电机反馈链路会异常。

**整改建议**

确认 RS485 模块类型：

- 自动方向模块：保持 `0u`，但在手册“待确认事项 A2”中记录结论。
- 需要 DE/RE：在 CubeMX 分配一个 GPIO，设置 `MODBUS_USE_RS485_DIR_GPIO = 1u`，并补齐 `MODBUS_RS485_DIR_PORT/PIN`。

### P1-05：I2C bus recovery 只有宏定义意图，没有实际恢复实现

**工程现象**

`sensors.h` 中定义了 `SENSOR_I2C_RECOVER_PULSE_COUNT` 与 `SENSOR_FAULT_RECOVER_PERIOD_MS`，但工程内没有发现实际 I2C 总线恢复函数。

**影响**

JY61P 与 ATK-MS53L1M 共用 I2C1。如果任一模块导致 SDA/SCL 卡死，当前固件主要依赖重新初始化模块，不能主动释放总线。

**整改建议**

增加 I2C1 bus recovery：

1. 关闭 I2C1 外设。
2. 将 PB6/PB7 临时配置为 GPIO 开漏输出/输入。
3. 对 SCL 输出 9 个脉冲，尝试释放 SDA。
4. 发送模拟 STOP。
5. 重新配置 PB6/PB7 为 I2C1 并 `HAL_I2C_Init()`。
6. 重新初始化 JY61P 和 ATK-MS53L1M。

---

### P1-06：树莓派通信协议仍是调试级 ASCII 协议，尚未达到正式帧协议要求

**工程现象**

当前 `remote_cmd` 通过换行符分割 ASCII 命令，例如 `VEL 0.2 0 0`、`HB`、`STOP`。这便于串口助手调试。

**影响**

正式比赛或树莓派联动时缺少：

- 帧头同步。
- 序号检查。
- 负载长度。
- CRC16 校验。
- 明确的消息类型枚举。

这会降低抗干扰能力和异常帧恢复能力。

**整改建议**

保留 ASCII 协议作为 `DEBUG_REMOTE_CMD`，新增生产协议：

```text
Header + Seq + MsgType + PayloadLen + Payload + CRC16
```

同时上报状态帧包含系统状态、故障位、IMU 摘要、激光摘要、电机摘要和心跳。

### P2-01：调度节拍和阻塞调用仍需优化

**工程现象**

主循环固定 `HAL_Delay(10)`，但循环中可能包含阻塞式 I2C 和阻塞式 Modbus 收发。电机反馈当前每 50 ms 轮询一个电机，四个电机完整轮询周期约 200 ms。

**影响**

当某个电机或传感器通信超时时，主循环会被拉长，影响树莓派命令解析、传感器刷新和安全状态机实时性。

**整改建议**

近期可先做轻量优化：

- 保持裸机，不急于上 FreeRTOS。
- 将传感器、远程协议、安全状态、电机刷新拆成基于 `HAL_GetTick()` 的非阻塞任务。
- 把阻塞接收超时控制在可接受范围内。
- 若后续四电机反馈必须高频读取，再考虑 DMA/中断或 FreeRTOS。

---

### P2-02：未用 GPIO 没有统一配置为模拟输入或明确上下拉

**工程现象**

`MX_GPIO_Init()` 当前只打开 GPIOA/GPIOB 时钟，没有对未用引脚做统一配置。

**影响**

一般不影响基础联调，但可能带来悬空噪声、功耗增加或偶发干扰。

**整改建议**

按手册建议，将未用 GPIO 配置为模拟输入或明确上下拉，并避免动到 `PA13/PA14/NRST` 调试复位引脚。

---

### P2-03：可选模块未纳入构建，且 UART3 测试模块与电机链路历史设计容易混淆

**工程现象**

`bringup_mode` 与 `sensor_uart3_stream_test` 在目录中存在，但 `.cproject` 未把它们纳入构建。若打开 `APP_ENABLE_BRINGUP_MODE`，当前工程配置可能出现找不到头文件或链接失败的问题。

**影响**

后续接手者可能误以为这些模块已经可用。尤其 `sensor_uart3_stream_test` 使用 UART3，容易和旧的电机 UART3 设计混淆。

**整改建议**

- 在 README 或工程说明中标注当前活动模块。
- 若需要 bring-up，自行把对应 UserModules 加入 `.cproject` source path 和 include path。
- UART3 若保留，只作为调试/备用链路，不作为电机标准链路。

---

### P2-04：Debug makefile 使用 Windows 绝对路径，跨环境构建失败

**工程现象**

`Debug/makefile` 中链接脚本路径为：

```make
D:\STM32CubeIDE\workspace_1.19.0\smart_logistics_car_integrated\STM32F103C8TX_FLASH.ld
```

在 Linux 环境执行 `make -n all` 会报：

```text
makefile:66: *** multiple target patterns. Stop.
```

**影响**

在原 Windows STM32CubeIDE 环境可能仍能构建，但工程可移植性较差。

**整改建议**

让 CubeIDE 重新生成 Debug 配置，或将链接脚本路径改为工程相对路径。

## 5. 建议整改顺序

### 第一优先级：让硬件链路跑通

1. 把 `Mecanum_Init(&huart3)` 改为 `Mecanum_Init(&huart1)`。
2. 启用 `USART2 global interrupt`，补齐 `USART2_IRQHandler()`。
3. 确认 RS485 模块是否自动方向；若不是，补齐 DE/RE GPIO。
4. 用串口助手或树莓派发送 `HB`、`VEL`、`STOP` 验证远程命令链路。
5. 用单电机地址逐个验证 ZDT_X42 地址 1/2/3/4、方向、速度单位和急停。

### 第二优先级：对齐传感器和接口标准

1. 把激光 Timing Budget/Inter-measurement 改为 `140000 us / 150 ms`。
2. 补齐 V3 推荐的 `g_imu_*` 与 `g_laser_*` 全局变量。
3. 调整激光无效数据处理逻辑，区分“传感器无效”和“障碍物过近”。
4. 增加 I2C bus recovery。
5. 确认 IMU 车体系映射关系，特别是 `roll/pitch` 与 `acc_forward/acc_right/acc_down`。

### 第三优先级：工程化和比赛可靠性

1. 将 ASCII 远程协议保留为调试协议，新增带 CRC16 的正式二进制协议。
2. 优化裸机调度节拍，减少阻塞调用导致的主循环抖动。
3. 统一未用 GPIO 状态。
4. 整理 UserModules，把当前未启用模块标记清楚。
5. 修复 Debug makefile 的绝对路径问题。

---

## 6. 总结

该工程不是空壳，已经完成了较多核心内容：JY61P、ATK-MS53L1M、传感器快照、麦轮运动学、ZDT_X42 Modbus 封装、底盘安全控制和树莓派 ASCII 命令接口都已经具备雏形。

但若严格以硬件平台技术手册 V3 为最高标准，当前工程还不能直接用于整车联调。最关键的问题是：电机链路代码仍绑定到 `USART3`，而标准硬件链路应为 `USART1/PA9/PA10`；树莓派命令接收使用中断模式但没有启用 USART2 中断；激光测距参数与手册不一致；V3 推荐的对外全局变量命名未完全落地。

建议先修复 P0/P1 问题，再进行四电机、IMU、激光和树莓派的整车联调。
